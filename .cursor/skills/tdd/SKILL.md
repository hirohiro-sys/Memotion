# tdd

## 0. 開始条件

- ルールファイル（`.cursor/rules/testing.mdc` と、変更パスに該当する `.cursor/rules/`）を読む
- 期待する振る舞いは要件・プランを出典にする。実装コードを正解にしない
- 期待結果が曖昧、仕様と実装が矛盾する場合は、推測でテストを書かず停止して報告する
- 自動テストは API の Vitest だけ。Web だけの変更は、テストを発明せず停止して報告する
- `docs/dev-flow.md` の step 8（テストを保ったリファクタ）には使わない。あれは振る舞いを変えず、既にあるテストが通ったまま進める

## 1. テストリストを作る

変更後に観測できる振る舞いを列挙する（正常系・境界値の両側・異常系・既存挙動の回帰）。
全件のテストコードを先に書かない。最も小さく設計を前進させる1件だけを選ぶ。

## 2. Red（失敗を実測する）

選んだ1件のテストを書き、対象テストだけを実行して失敗を確認する。
未実装の振る舞いが原因で失敗する状態にする（コンパイルエラーは Red ではない）。
最初から通ってしまったら、実装済みか、assert が弱いかを判定する。

対象ファイルの隣に `*.test.ts` を置く。1件の実行は次のとおり。

```bash
pnpm --filter @repo/api exec vitest run src/features/<機能>/<ファイル>.test.ts
```

## 3. Green（最小の実装）

その1件を通すのに必要な実装だけを書く。固定値の返却・テスト専用分岐・assert 削除・skip は「最小実装」ではない。同じ失敗を2回繰り返したら、試行を増やさず前提と設計を見直す。

## 4. Refactor（Green を保って整理）

すべて Green の状態でのみ行い、変更のたびにテストを実行する。

## 5. リストが空になるまで繰り返す

作業中に見つけたシナリオはリストへ追加する。完了時は、テストリストの全項目と実装されたテストを対応づけて報告する。テスト通過だけを完了証明にしない。
