# Design Doc: 予定（schedule）タグとカレンダー

プラン: [docs/plans/schedule-calendar.md](../plans/schedule-calendar.md)（作業の詳細と、テストケースはそちら）

## 1. 背景と範囲

- 今のメモが持つ日時は、書いた時刻（`createdAt`）だけで、「いつの予定か」を残せない
- 予定を忘れないよう、前日に LINE で知らせたい。予定がある日を、カレンダーでひと目で見たい
- 範囲: タグ `schedule`（予定）、予定の前日の LINE 通知、サイドバーの「カレンダー」（`/calendar`）
- カレンダーは、あとから日ごとのメモと日報（今後実装予定）を見られる画面に育てる前提で作る

## 2. 目標と非目標

目標:
- 予定に日付（必須）と時刻（任意）を持たせ、Web で登録・変更・削除できる
- 予定の前日の設定時刻（初期値 20:00）に、翌日の予定を1通にまとめて LINE に送る
- カレンダーで、予定がある日に点を付け、日を選ぶとその日の予定の一覧を出す

非目標:
- LINE からの予定の登録（LINE のタグの廃止は別の issue）
- 終了時刻、繰り返し、当日の朝や直前の通知、予定の完了・キャンセル
- カレンダーでの日ごとのメモと日報、日本時間以外のタイムゾーン
- 予定から他のタグへ戻す操作、ほかのタグ同士の切り替え

## 3. 設計

### 全体像

- 予定は、`memos` テーブルの1行にする（新しいテーブルは作らない）。`memos` に日付と時刻の列を足し、タグ `schedule` を足す
- 予定にする入口は2つ。Web の入力欄でタグ「予定」を選ぶ（`POST /api/memos`）。メモタブで、つぶやきを「予定にする」（`PUT /api/memos/:id/schedule`）。日時の変更も同じ `PUT`
- カレンダーは、今のメモ一覧の取得（`GET /api/memos`）から予定のメモを選んで表示する。新しい取得 API は作らない
- 通知は、cron（毎分）が動かす。設定の行だけで「送るか」を判断し、送ると決まったときだけ、`memos` の service から翌日の予定を取って LINE に送る
- 予定はグループに入れられない（「やること」と同じ扱い）。そのため、`GET /api/memos`（グループに入っていないメモ）に、予定は必ず含まれる

### API と契約（`packages/shared`）

- `memoTagSchema` に `schedule` を足す。`memoSchema` に `scheduledDate` と `scheduledTime`（予定のときだけ）を足す
- `createMemoRequestSchema` に同じ2項目を足す。タグが `schedule` のときは日付が必須で、ほかのタグに日時が付いたら不可
- `PUT /api/memos/:id/schedule` を新設する（本文は日付と、省略か `null` の時刻）。つぶやきを予定にするときと、予定の日時を変えるときに使う
- `PATCH /api/notifications` に、予定の通知のオン/オフと時刻を足す
- エラー: 過去の日付は 400（`schedule_date_past`）、予定にできないメモは 409（`not_schedulable`）、他人のメモと存在しないメモは 404

### データ

- `memos`: `scheduled_date`（`YYYY-MM-DD`）と `scheduled_time`（`HH:MM`）を、NULL 可の文字列で持つ。`(user_id, scheduled_date)` に索引を足す
- `schedule_daily_settings`: `user_id`（一意）、`enabled`、`time`、`last_target_date`、`disabled_reason`
- `tags`: `schedule` の行を足す
- マイグレーションは、NULL 可の列の追加、新しいテーブル、タグの行だけ。`memos` を作り直さない

### 処理の流れ: 通知

1. cron が毎分動き、ユーザーごとに設定の行を読む。行が無ければ既定値（オン、20:00）で扱う
2. 設定だけで、送るかを判断する。無効なら送らない。直近の通知の時刻の翌日（対象日）が、すでに処理済み（`last_target_date` が対象日以降）なら送らない。実行した時刻の日付が、通知の時刻の日付と違えば送らない（日付をまたぐと「明日の予定」が嘘になるため）
3. 送ると決まったら、送る前に、条件付きの1文で `last_target_date` を対象日に更新して「先取り」する。更新された行が0なら、別の実行が取ったので何もしない
4. 先取りに成功したら、対象日の予定を取る。0件ならそのまま終わる（処理済みのまま）。あれば、LINE に1通にまとめて送る
5. 一時的な送信失敗のときは、先取りを元に戻し、次の分に再試行する。LINE に送れない状態のときは、設定をオフにする

### 制約

- 本番の D1 へのマイグレーションを、新しい API の公開より先に当てる。逆にすると、メモの一覧と作成が止まる
- 予定のメモが1件でも DB にあると、旧版の API には戻せない（旧版は `tag: "schedule"` を検証できない）。DB は前進のみ
- 日付と時刻は、日本時間（JST）に固定する
- LINE の送信先は、ループ中のユーザーの `lineUserId` だけを使う

## 4. 検討した代替案

| 論点 | 採った案 | 採らなかった案と、理由 |
| --- | --- | --- |
| 予定の登録の入口 | Web だけ（LINE は `tweet` のまま） | LINE の `#schedule 11/3 14:00 歯医者` のように本文から日時を読む案。「明日」「来週月曜」などの表記揺れを制御するのが大変なため |
| 予定の日時の持ち方 | 日付と時刻を別々の列（JST 固定） | 1つの UTC の日時と終日の印を持つ案。時刻が任意なので、日付だけと日時の2つを自然に表せない。カレンダーと通知の「明日」の判断が、時刻の変換なしで済む |
| 通知のまとめ方 | 毎日1回、翌日の予定を1通にまとめる | 予定ごとに1通ずつ送る案（予定が増えると通知が増えすぎる）。当日の朝にも送る案（今回は前日だけ） |
| 二重送信の防止 | `last_target_date` を、送る前に条件付きの1文で先取りする | 既存の通知と同じ形（送ったあとに `lastSentAt` を書く）。書き込みの失敗や、前の分の実行との重なりで、同じ通知が毎分届きうる。時刻を変えたときの再送も防げない（レビューで判明） |
| カレンダーの取得 | 今のメモ一覧の取得（`GET /api/memos`）を使い回す | 月ごとに予定を返す専用の API。予定はグループに入れられないので、一覧に必ず含まれ、サイドバーが同じデータをすでに取得している。メモが増えて重くなったら切り替える |
| カレンダーの置き場所 | サイドバーの専用ページ | メモ一覧の3つ目のタブ。今のタブは「メモを見る単位」の切り替えで、日付を軸にした見方とは役割が違う。日報への拡張もしやすい |
| タグの切り替えの範囲 | つぶやき → 予定だけ | 4タグ共通の切り替え。LINE のタグ廃止と同じ別の issue で作る。予定へ戻す操作は、今回は不要と判断 |
| 予定とグループ | 予定はグループに入れられない | 入れられるようにする案。グループの中身は1件ずつ操作できず、日時の変更ができなくなる。メモタブに残す方針と矛盾する |
| Web の入力欄 | タグ「予定」を足す（日付と時刻の欄が出る） | つぶやきで書いてから「予定にする」の2段階だけにする案。Web で予定を書くたびに2段階になるため |
| カレンダーの日の表示 | 予定がある日に点を1つ付ける | 件数の数字（日付と混ざる）、予定の本文を並べる案（スマホで収まらない） |
| 登録時の注意 | 通知が届かない日付なら、Web が注意を出す | 出さない案。夜に明日の予定を登録すると、通知が黙って外れるため。判断は、取得済みの通知の設定と JST の時刻で、Web が行う |
| 日付の関数の置き場所 | Web と API にそれぞれ書く | `packages/shared` に置いてテストする案。壊れても影響が小さく、画面で気づけるため、今回は自動テストを書かない |

## 5. 横断的な考慮事項

セキュリティ（認可）:
- `PUT /api/memos/:id/schedule` は、セッションが無ければ 401。更新の SQL は `user_id` で絞る。他人のメモと存在しないメモは、区別せず 404
- 更新の SQL は、状態の確認と同じ条件（自分のメモ、グループなし、タグが `tweet` か `schedule`）を `WHERE` に持つ。「グループに追加」の SQL も、予定を対象から外す。同時に動いても、グループに入った予定は生まれない
- 通知の予定の取得は、`user_id` と対象日とタグで絞る。送信先は同じユーザーの `lineUserId`

プライバシー（ログ）:
- 予定の本文と日付は、ログに出さない。D1 の例外は投げ直さず、ID だけをログに出す（Drizzle の例外の message に、日付や本文が入るため）

運用:
- ログ `schedule.daily` で、送信の結果（`success`、`unreachable`、`transient`、`failed`）と、送らなかった理由（`empty`、日付をまたいだ `stale`）を追える。`stale` は、処理済みにして1回だけ出る
- 通知は、時刻を過ぎてから登録した予定には届かない。登録時の注意で、その旨を知らせる
- 設定をオンにしたときと時刻を変えたときは、すぐには送らない（既存の通知と同じ）
