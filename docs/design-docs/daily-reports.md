# Design Doc: 日報

プラン: なし。実装の基準にするプランは、この文書に合わせて `docs/plans/daily-reports.md` に書く｜issue: [#31](https://github.com/hirohiro-sys/Memotion/issues/31)

## 1. 背景と範囲

- メモは LINE と Web に残るが、その日の仕事や個人の記録として読み返す文章にはなっていない（issue #31）
- 日報は貯める文章である。月報と職務経歴書は、その文章をあとから読む側で、今回は作らない
- 範囲: メモ一覧で選んだメモから日報を生成して保存し、専用ページで編集と一覧をする。同じ日付・同じ種類（仕事 / 個人）は1本

## 2. 目標と非目標

目標

- 選んだメモを材料に、生成AIが日報の本文を書く。書いた文章はその場で直し、下書きとして残すか、書き終わりの印（確定）を付けられる
- 同じ日付・同じ種類の日報が既にあるときは、2本目を作らずその日報を開く。開いた時点では本文を変えず、まだ入っていないメモだけを足せる
- 確定したあとも本文は直せる。元のメモを消しても、日報の本文は残る

非目標

- 月報、職務経歴書、LINE からの作成、日報の LINE 通知
- フレームワークの自作、本文の検索、オフラインでの保存、表示のオンオフ
- カレンダーのマスの印と、カレンダーの日の枠への日報

## 3. 設計

### 全体像

- 新しい機能 `features/daily-reports/` を作る。日報の保存、材料メモとの対応、生成の呼び出し回数を持つ。メモの読み取りは `memos` の service を経由し、`memos` テーブルへは直接クエリしない
- 入口はメモ一覧の選択バーである。チェックが1件以上あるときだけ「日報を追加」を出す。オフラインのときは押せない。押すとモーダルで、選んだメモ、日付、種類、フレームワークを確認する
- 一覧と編集は専用ページ（`/daily-reports`、`/daily-reports/$id`）である。サイドバーはメモ一覧、カレンダー、日報、設定の順にする
- 本文を組み立てる判断（先頭行、末尾への連結、空や長さの拒否）は純粋関数に置く。生成APIの呼び出し、回数の増減、DB への書き込みは service が行う
- カレンダー（`/calendar`）と、メモ一覧の削除・グループ追加は変えない

### API と契約（`packages/shared`）

日付は `YYYY-MM-DD`（予定と同じ、実在する日）。種類は `work` | `personal`、フレームワークは `log`（記録）| `achievement`（実績）、状態は `draft`（下書き）| `confirmed`（確定）。本文は trim して1文字以上、2万字まで。新規作成と足すに渡すメモ ID は1件以上90件まで（D1 は1クエリのバインド変数が100までで、`memos` の削除が同じ上限を90件にしている）。

- `GET /api/daily-reports`: 自分の日報の一覧（本文は含まない）と、今日（JST）の残り生成回数
- `GET /api/daily-reports/:id`: 1本。本文と、材料にしたメモ ID。他人の日報と無い日報は区別せず 404（`daily_report_not_found`）
- `POST /api/daily-reports`: 新規作成。成功時の応答は保存した日報。既にあれば 409（`daily_report_exists`）で既存の ID を返し、生成も保存もしない
- `POST /api/daily-reports/:id/append`: 要求のフレームワークで、まだ材料でないメモだけを文章にし、本文の末尾に足す。状態は変えない
- `POST /api/daily-reports/:id/regenerate`: 要求のフレームワークと、今の材料で全文を置き換える。状態は変えない。置き換え前の確認は画面だけが行い、この API は呼ばれたら置き換える
- `PUT /api/daily-reports/:id`: 本文、状態、フレームワークを保存する。生成はしない
- `DELETE /api/daily-reports/:id`: 日報と材料の対応を消す。メモは消さない。生成回数は戻さない
- エラー: `daily_report_not_found`（404）、`daily_report_memo_ineligible`（400）、`daily_report_too_long`（400）、`daily_report_exists`（409）、`daily_report_ai_limit`（429）、`daily_report_unavailable`（502）
- Web は `apiFetch` し、入出力は Zod で parse する

### データ

- `daily_reports`: `user_id`、`report_date`、`kind`、`framework`、`body`、`status`、`created_at`、`updated_at`。`(user_id, report_date, kind)` を一意にする
- `daily_report_memos`: `report_id`、`memo_id`。組を一意にする。`memo_id` は `onDelete: cascade`。メモを削除すると対応の行だけ消え、日報の本文は残る。同じメモを仕事と個人の両方から参照してよい
- `daily_report_ai_uses`: `user_id`、`used_on`（呼び出しを行った JST の日付）、`count`。`(user_id, used_on)` を一意にする。`count` は成功した呼び出しと、まだ終わっていない呼び出しの数。失敗したら1戻す
- マイグレーションはこの3テーブルと一意制約だけ。`memos` は変えない
- 日報を削除するときは、日報の行と対応の行を一緒に消す（対応は `report_id` の `onDelete: cascade`）

### 処理の流れ

作成モーダルの初期値は、種類が仕事、フレームワークが実績である。種類を個人に変え、フレームワークをまだ手で変えていなければ、フレームワークは記録になる。日付の初期値は、選んだメモの作成日（JST）が全部同じならその日、そうでなければ今日（JST）である。過去の日も未来の日も指定できる。

既にある日報を開くときは、モーダルで選んだフレームワークでは上書きしない。保存されている型を出す。

材料にできるのは、自分のメモのうち、グループに入っていないものである。タグでは除外しない（つぶやき、技術、やること、予定、その他）。生成に渡すのは、本文、作成日時（JST）、URL があるときの URL である。予定のメモには予定日と時刻も渡す。画像と画像 URL は渡さない。

`GET /api/memos` はグループのメモを返さない。作り直しで、グループへ移したあとのメモを読むのには使わない。読み取りは `memos` の service に、持ち主のメモを ID で取る関数を足す。

新規作成

1. セッションが無ければ 401。入力が契約に反すれば 400
2. メモを `memos` の service から取る。他人のメモと無いメモが1件でもあれば 404 で、日報は作らない。自分のメモでもグループに入っていれば 400（`daily_report_memo_ineligible`）で、全体を拒否する
3. 同じユーザー・日付・種類の日報があれば 409。回数は減らさない。画面はその日報を開き、今回選んだメモのうち対応が無いものだけを「まだ入っていない」と出す。この一覧は遷移先の画面状態にだけ持ち、再読み込みすると消える。本文とフレームワークは、開いただけでは変えない
4. secret が無ければ、回数を増やさず 502（`daily_report_unavailable`）。あるときは回数の行を1文で増やす。行が無ければ `count = 1` で作り、あれば `count < 2` のときだけ1増やす。増えなければ 429（`daily_report_ai_limit`）
5. 生成する。モデルが書くのは本文だけである。記録は時刻ごとの短い箇条書き、実績は「やったこと」「気づき」「次にやること」。先頭行（`10月29日（木） 仕事`。日付、曜日、種類。年は付けない）は `report_date` からサーバーが付ける。Worker の時刻には依らない
6. 保存する本文は先頭行を含めて2万字まで。失敗か空の応答は回数を1戻して 502。2万字超は回数を1戻して 400（`daily_report_too_long`）。どちらも日報は作らない
7. 下書きとして日報と対応を書く。一意制約に敗れたときは行を残さず、回数を1戻して 409 を返す

足す:

1. セッション、契約、メモの持ち主とグループを、新規作成と同じ基準で見る。グループのメモが1件でも混ざっていれば全体を 400 にし、回数は動かさない。検査のあと、既に材料のメモを除く。残が0件なら 400 で、回数は動かさない
2. 回数を新規作成と同じ1文で1増やす。生成するのは残ったメモだけで、要求のフレームワークの書き方にする。先頭行は付けない。この時点ではフレームワークも本文も変えない
3. 純粋関数が今の本文の末尾へ空白行を挟んで連結する。連結結果が2万字を超える、または生成に失敗したときは、回数を1戻す。本文、対応、フレームワークは変えない
4. 成功したら本文、フレームワーク、対応を更新する。状態は変えない。足したメモは「まだ入っていない」から外れる

作り直す: 今つながっている材料が0件なら、回数を動かさず 400。あるときは回数を1使い、要求のフレームワークで全文を置き換える。先頭行はサーバーが付け直す。失敗したときは本文もフレームワークも以前のまま残し、回数を1戻す。成功したら状態は変えない。材料のメモをあとからグループへ移していても、作り直しの材料からは外さない。

保存（`PUT`）: 本文、状態、フレームワークだけを書く。フレームワークを変えても本文は作り直さない。一時保存は `draft`、確定は `confirmed`。確定した日報を一時保存すると、印は下書きに戻る。空白だけの本文は 400。

一覧は `report_date` の新しい順、同じ日は仕事を個人より前に出す。

### 制約

- 生成の回数は日報の日付ではなく呼び出しを行った日（JST）の2回までである。数えるのは新規作成、足す、作り直す。既存を開く操作と、失敗して回数を戻したものは数えない。キーが無い、または生成先が失敗したときは 502 で、ほかの機能は壊さない
- 生成先のサービスは未決定である。実装に入る前に1つに決める。決まっても、キーは Worker の secret だけ、宛先は固定、応答は信用せず長さと空だけを検査する、という境界は変えない
- 先頭行に年は付けない。年は `report_date` にある
- 実装時に `.agents/rules/logging.md` の event 一覧へ `daily_report.generate` を足す。新しい helper は作らない。`.agents/rules/line-security.md` のセッション必須の経路に、日報のルートを足す
- 回数の増減と日報の書き込みは別の文である。増やしたあとに Worker が落ちると、その日の回数が1残ったまま戻らない。利用者はログインを許可された人だけなので、許容する
- 画面を再読み込みすると「まだ入っていない」は消える。もう一度メモ一覧から同じ日報を開けば、対応が無いメモだけが再度出る
- 旧版の API は日報のテーブルを読まない。マイグレーションの前に新しい Worker を出すと、日報のルートだけが失敗する

## 4. 検討した代替案

| 論点 | 採った案 | 採らなかった案と、理由 |
| --- | --- | --- |
| 置き場所 | 専用ページで一覧と編集をする | カレンダーの日の枠に置く案。読み返す文章の一覧には向かない。カレンダーは予定と、その日に書いたメモのままにする |
| 1日の本数 | 日付と種類で1本 | 同じ日に何本でも作る案。あとから「その日の仕事」がどれか決まらない |
| 材料の日付 | 別の日のメモが混ざっていても1本にできる。日付はモーダルで選ぶ | 作成日が違うメモを拒む案。メモ一覧のチェックは日をまたぐ |
| 既にある日報 | 開く。本文は足すまで変えない | 2本目を作る案。選んだメモで全文を気づかないうちに置き換える案（直した段落が消える） |
| 足す範囲 | 足すメモだけを書き、末尾に連結する | 全文を作り直す案。メモ本文をそのまま貼る案（前半と書き方が割れる） |
| フレームワーク | 記録と実績の2つ。仕事の初期値は実績、個人は記録 | 学習を含む3つ（今回の合意で外した）。種類と同じ2つにする案（仕事 / 個人と役割が重なる）。見出しを毎回手で書く案 |
| 確定 | 書き終わりの印。本文はロックしない | ロックする案。確定後は開けず、消して作り直す案 |
| メモを消したとき | 本文は残し、対応だけ消える | 日報も消す案。対応を残して「元のメモが無い」と出す案 |
| フレームワークの変更 | 本文は作り直さない。次に足す分から、そのとき選んだ型を使う | 変更と同時に全文を作り直す案 |
| 生成の回数 | 操作した日（JST）に2回。失敗は戻す | 日報の日付ごとに2回（過去の日の分を同じ日にまとめて作れない）。失敗も1回に数える案 |
| 回数の守り方 | `count < 2` の条件付き更新 | 成功したあとに数える案。同時に押すと2回を超える |
| テーブル | 日報、対応、回数の3つ。`memos` は変えない | `memos` に日報の列を足す案。契約と関係ない列が増える |
| 本文の作り方 | 生成AIが書く | 見出しの下にメモを並べる案。ボタンのあとで文章が現れない |
| 画像 | 渡さない | 画像 URL を渡す案。配信はセッション必須で、生成先へ渡す URL にできない |

## 5. 横断的な考慮事項

セキュリティ（認可）

- すべてのルートは、セッションが無ければ 401。日報、対応、回数の読み書きは、セッションのユーザーの `user_id` で絞る
- 他人の日報と無い日報は 404。他人のメモと無いメモが材料に混ざっていれば、要求全体を 404 にし、日報も回数も変えない
- 生成先の API キーは Worker の secret だけに置く。宛先は実装時に決めた1つのオリジンに固定する。応答本文は日報の本文として保存するだけで、実行しない

プライバシー（ログ）

- メモ本文、URL、生成した本文、プロンプト、API キーはログに出さない
- 失敗時のログは`event: "daily_report.generate"`、`userId`、`status`、`reason`（`limit` / `upstream` / `empty` / `too_long`）だけにする。成功のたびに出さない

運用

- 生成先が止まっていても、一覧、保存、削除はできる。新しく書く操作だけが 502 になる
- 回数は JST の日付が変わると、行が無い状態から再び2回になる。戻すバッチは要らない
- 本番に出す前に、人が生成先の secret を置き、`db:migrate:remote` を行ってから Worker をデプロイする
