# Design Doc: connpass の参加イベントを予定に取り込む

プラン: [docs/plans/connpass-import.md](../plans/connpass-import.md)（作業の詳細と、テストケースはそちら）｜issue: #68

## 1. 背景と範囲

- 勉強会やイベントの参加は connpass で管理している。その日程を Memotion の予定に手で写すのは手間で、写し忘れると前日の LINE 通知も来ない
- connpass API v2 は、API キー（個人は無償、申請と審査あり、1つだけ）が必須で、1キーにつき1秒1リクエストまで。OAuth は無く、本人のイベントはユーザー名で絞って取る。API 以外の手段での取得は規約で禁止
- 範囲: 参加登録したイベントを、1時間ごとの Cron と手動のボタンで、予定（`tag: schedule`）として取り込む。connpass 側の変更・中止・参加取り消しを予定に反映する。設定画面に connpass の節を足す

## 2. 目標と非目標

目標:
- connpass で参加登録した今日以降のイベントが、何もしなくても予定になり、カレンダーと前日の LINE 通知に出る
- connpass 側で日時・名前が変わったら予定も変わり、中止・参加取り消しになったら予定が消える
- Memotion で消した予定は、もう取り込まれない

非目標:
- 過去のイベントと、13 か月より先のイベントの取り込み
- URL・会場・終了時刻を予定に持たせること
- 取り込んだ予定を、Web と LINE で区別して見せること
- 補欠・抽選待ちを参加確定と分けること（API が本人の参加状態を返さない）
- 発表・管理するイベント、connpass 以外のサービス

## 3. 設計

### 全体像

- 新しい機能 `features/connpass/` を作る。connpass API の呼び出し、ユーザー名の設定、取り込んだイベントと予定の対応表を持つ
- 予定は、今の予定と同じ `memos` の行として作る。予定の行は `memos` の service が返す「文」で作り、connpass の対応表の文と一緒に D1 の `batch` で書く（依存は `connpass` → `memos` の一方向）
- 取り込んだ予定は、ふつうの予定として、カレンダーと前日の通知（`notifications`）にそのまま載る。通知のコードは変えない
- Cron の入口 `apps/api/src/scheduled.ts` を新しく作り、通知と connpass の取り込みを、互いの失敗で止めないように呼ぶ

### API と契約（`packages/shared`）

- `GET /api/connpass/settings` — 自分のユーザー名と、最後の取り込みの時刻・結果
- `PUT /api/connpass/settings` — ユーザー名を保存する（connpass に実在するかを確かめる）か、`null` で消す
- `POST /api/connpass/sync` — 今すぐ取り込み、作成・更新・削除の件数と、最後まで取れたかを返す
- エラー: `connpass_user_not_found`（400）、`connpass_not_configured`（409）、`connpass_sync_too_soon`（429）、`connpass_unavailable`（502）
- `Memo` の契約は変えない（取り込んだ予定の `source` は `web`）
- connpass の応答の Zod は `features/connpass/` に置く（Memotion の公開契約ではないため）

### データ

- `connpass_settings`: `user_id`（一意）、`nickname`、`last_synced_at`（取り込みの先取りに使う）、`last_sync_status`
- `connpass_imports`: `user_id`、`event_id`、`memo_id`（`memos.id` を参照、`onDelete: set null`）、前回取り込んだ名前・日付・時刻。`(user_id, event_id)` を一意にする
- `memo_id` が NULL の行は「ユーザーが予定を消したので、もう取り込まない」を表す。メモの削除の経路を変えずに、消したことが残る
- マイグレーションは、新しいテーブル2つと索引だけ。`memos` は変えない

### 処理の流れ: 1ユーザーの取り込み

1. 先取り: 条件付きの1文で `last_synced_at` を今に進める。Cron は前回から1時間以上、手動は 60 秒以上たっていなければ取れず、何もしない
2. 取得: 今月から 12 か月先までの月（`ym`）を指定し、ユーザー名で参加イベントを 100 件ずつ取る。ページの間は 1 秒あける。どれかのページが失敗したら、全体を失敗にして何も反映しない
3. 計画: 純粋関数 `planConnpassSync` が、今日以降のイベントと対応表を突き合わせ、作成・更新・削除を決める
   - 対応表に無い → 作る。予定を消した行（`memo_id` が NULL）→ 何もしない
   - 名前・日付・時刻のどれかが前回と違う → 予定を上書きする
   - 中止 → 予定と対応表の行を消す
   - 取得結果から消えた（参加取り消し）→ 最後まで取れたときだけ、予定と対応表の行を消す。開催済みの予定は残す
4. 反映: イベントごとに、予定と対応表の書き込みを `batch` で1つにまとめる
5. 記録: `last_sync_status` に成功か失敗かを残す。失敗しても先取りは戻さず、次の時刻に再試行する

### 制約

- 実装の前に、人が実際のキーで確かめる（プランの「着手前の確認」）: 補欠が検索結果に含まれるか、参加取り消しで結果から消えるか、`started_at` の形、存在しないユーザー名の応答
- connpass の制限（1キーにつき1秒1リクエスト）を守る。キーは全ユーザーで1つ
- 本番に出す前に、人が `wrangler secret put CONNPASS_API_KEY` と `db:migrate:remote` を行う。キーが無くても、取り込みが止まるだけでほかは壊れない
- `memos` と `Memo` の契約は変えないので、旧版の API に戻しても、取り込んだ予定はふつうの予定として読める

## 4. 検討した代替案

| 論点 | 採った案 | 採らなかった案と、理由 |
| --- | --- | --- |
| 取得の手段 | connpass API v2（キーは持っている） | iCal やページの読み取り。API 以外での取得は規約で禁止 |
| ユーザー名の置き場所 | 設定画面で入力し、DB に保存 | `wrangler.toml` に書く案。変えるのに再デプロイが要る |
| 取り込みの頻度 | 1時間ごとの Cron と、手動のボタン | 1日1回（前日の通知のあとに申し込んだ翌日のイベントが通知されない）。手動だけ（押し忘れると通知が来ない） |
| 取り込む範囲 | 今日以降、13 か月先まで | 過去も含める案（参加履歴として使う）。今の「過去の日付の予定は作らない」と揃え、ページ送りの回数も減らす |
| 予定の本文 | イベント名だけ | 名前と URL、名前と会場と URL。通知が長くなる |
| 二重登録の防止 | 別の表に、イベント ID と予定の対応を持つ | `memos` に connpass の列を足す案。`memos` と `Memo` の契約が変わり、ほかのメモに関係ない列が増える |
| 消した予定 | 対応表の参照を NULL にして、もう取り込まない | また作る案。要らないイベントを Memotion だけで消せない |
| 変更の検出 | 前回取り込んだ名前・日付・時刻と比べる | connpass の `updated_at` と比べる案。概要の編集でも変わり、手で直した日時が上書きされる |
| 変更の反映 | connpass の値で上書きする | 反映しない案。日時の変更に気づけない |
| 中止・参加取り消し | 予定を消す | 本文に「（中止）」を付けて残す案（通知に中止の予定が載る）。何もしない案（自分で消す手間） |
| 一部しか取れなかったとき | 失敗なら何も反映しない。上限で切れたら削除だけしない | 取れた分で削除まで行う案。一時的な失敗で、未来の予定をまとめて消しうる |
| 打ち間違いのユーザー名 | 保存するときに実在を確かめる | 確かめない案。結果が0件になり、取り込んだ予定をまとめて消しうる |
| Web と通知での区別 | 区別しない | 印を付ける案。`Memo` の契約と通知の文面を変える必要があり、今は要らない |

## 5. 横断的な考慮事項

セキュリティ（認可）:
- 3つのルートは、セッションが無ければ 401。設定・対応表・予定の読み書きは、すべてセッションのユーザーの `user_id` で絞る
- 対応表の一意制約は `(user_id, event_id)`。同じイベントに参加する別のユーザーと混ざらない
- 予定の更新・削除の文は、`user_id`・タグ `schedule`・グループなしで絞る
- connpass への呼び出しは、宛先を `https://connpass.com/api/v2/` に固定し、ユーザー名は `URLSearchParams` で渡す。応答は信用せず Zod で検査する。API キーは Worker の secret だけに置く

プライバシー（ログ）:
- API キー、ユーザー名、イベント名、日付、connpass の応答本文は、ログに出さない
- D1 の例外は投げ直さず、`userId` と件数だけを出す（例外の message に本文が入るため）

運用:
- ログ `connpass.sync` で、ユーザーごとの結果（件数、最後まで取れたか、失敗の HTTP ステータス）を追える
- 失敗しても、次の時刻に再試行する。結果は設定画面にも出る
- 前日の通知の時刻を過ぎてから取り込んだ翌日の予定は、通知されない（今の予定と同じ）
