# Design Doc の方針

プランのレビューを終えたあと、実装の前に Design Doc（DD）を書く。目的は、自分が設計を理解し、納得した状態で AI に実装させることである。手順は `docs/dev-flow.md` の step 4。

## 置き場所

- `docs/design-docs/[機能名].md`。ファイル名はプラン（`docs/plans/`）とそろえる
- プランが「何をどう作るか」の作業計画なのに対し、DD は「なぜこの設計にしたか」を自分の言葉で残す

## 書き方

1. **不明点をなくす**: プランを読んで少しでもわからない点があれば、AI に聞く。すべて解消するまで先へ進まない
2. **DD に反映する**: 解消した内容を、下の章立てで DD に書く
3. **削る**: 短いほど読みやすい。自分が理解して説明できる部分は、AI が書いた余計な文章を削る
4. **セルフレビュー**: 自分の言葉で説明できるかを、最後の「理解度チェック」で確かめる。説明できない箇所があれば 1 に戻る
5. 納得できたら、実装に進む

## 章立て

Google の Design Doc の形に合わせる（参考: [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)）。該当しない章は「なし」と書く。

1. **背景と範囲**: 何を作るか、どんな状況で必要になったか。事実だけを短く
2. **目標と非目標**: 達成すること。あえてやらないこと（非目標）も書く
3. **設計**
   - 全体像: 既存のどの部分とどうつながるか
   - API: 追加・変更するエンドポイントと契約（`packages/shared` の Zod）
   - データ: テーブル、列、制約、マイグレーション
   - 処理の流れ: 要所だけ。コードを貼らない
   - 制約: 守らなければならない前提（既存ルール、互換性、デプロイの順序）
4. **検討した代替案**: 採らなかった案と、採らなかった理由
5. **横断的な考慮事項**: セキュリティ（認可）、プライバシー（ログに出さないもの）、運用（ログ、障害時の振る舞い）
6. **理解度チェック**: 下の問いに、自分の言葉で答える

## 理解度チェック

DD の最後の章に、次の問いと自分の答えを書く。答えに詰まったら、その設計判断は理解できていない。

- この機能がないと、誰が何に困るか
- 主な設計判断を3つまで挙げ、それぞれ採らなかった案と、選んだ理由を説明できるか
- 壊れたときに影響が大きいのはどこか。そのとき何が起きるか
- 認可（誰が何を見られ、変えられるか）をどこで守っているか
- 本番に出す順序（マイグレーション、デプロイ）に制約はあるか
