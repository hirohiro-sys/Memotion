# 開発フロー（参考プロンプト）

8 step のプロンプトである。`[ ]` は使うときに埋める。記入例 `docs/plans/_template.md` は照合・レビューの対象にしない。

このリポジトリでの参照先:

| プロンプト中の参照 | 置き場 |
| --- | --- |
| プラン | `docs/plans/`。形式は `docs/plans/_template.md` |
| ルール | `.cursor/rules/` |
| サブエージェント | `.cursor/agents/` の design-reviewer、edge-case-reviewer、security-reviewer |
| 要件の出所 | issue の Design Doc、または `docs/` の該当文書 |
| テスト | API は Vitest。Web はブラウザで確認する。Playwright はない |

## 1. プランドキュメントの作成（インタビュー形式）

```text
[機能名]を作りたい。概要: [2〜3行で]。
参考: [要件の出所。issue の Design Doc、または docs/ の該当文書] と、関連コード [ディレクトリ]。
まず実装に入らず、プランを書くために必要な質問を私にすること。
技術面・エッジケース・トレードオフについて、答えにくい質問ほど価値がある。
質問が尽きたら、プランを docs/plans/[ファイル名].md に
8項目（概要・背景・詳細設計・テスト影響範囲・新規テストケース・
実装順・コミット前テスト実行・スコープ外）で書き出すこと。
形式は docs/plans/_template.md に合わせる。
実装順には、どのタスクをどのモデル・サブエージェントに任せるかの
割り当てまで書くこと。
```

## 2. プランの相互レビュー（観点別）

```text
docs/plans/[プランファイル].md をレビューすること。私は書いた本人ではない前提で読む。
docs/plans/_template.md は対象にしない。
観点: [設計整合性/セキュリティ/運用/ビジネス整合性から1つ]。
判定の基準: [.cursor/rules/ の該当ルール、または要件の出所]。
指摘は P0（実装前に必ず直す）/ P1（推奨）/ P2（軽微）に分類し、
プランのどの記述が・どの基準と・なぜずれるかを1件ずつ示すこと。
```

## 3. テスト網羅のレビュー

```text
docs/plans/[プランファイル].md の「新規テストケース」だけをレビューすること。
要件の受け入れシナリオと突き合わせ、
(1) シナリオに対応するテストが欠けていないか
(2) 境界値の両側・異常系が入っているか
(3) 実装しないと決めたスコープ外がテストに紛れていないか
を確認し、足りないテストケースを提案すること。
自動テストは API の Vitest（.cursor/rules/testing.mdc）だけである。
Web の確認はブラウザで行い、Playwright のケースは提案しない。
```

## 4. 実装

失敗を先に確認する進め方は、下のプロンプトには書かない。使うときは依頼文で TDD、テスト駆動、または Red-Green-Refactor と指定する。そのときだけ `.cursor/skills/tdd/SKILL.md` に従い、プランの新規テストケースを1件ずつ失敗させてから通す。指定が無いときは、実装とテストを書いてから step 5 へ進む。

```text
docs/plans/[プランファイル].md の実装順に従って実装すること。
プランの割り当てどおり、[調査/ユーティリティ]はサブエージェントに任せてよい。
プランにない変更が必要になったら、実装せずに立ち止まって報告すること。
API の振る舞いを変えたら、対象ファイルの隣の *.test.ts を同時に書く（.cursor/rules/testing.mdc）。
Web だけの変更はテストを発明せず、ブラウザで変更フローを確認する。
実装のあとに、テストを失敗させに戻らない。
```

## 5. テストの全通過

```text
プランの「コミット前テスト実行」を実行し、全通過の出力を見せること。
プランにコマンドが無いときは、次を実行する。

pnpm lint
pnpm typecheck
pnpm --filter @repo/api test
pnpm build
```

## 6. 実装のAI相互レビュー（観点別並列）

```text
実装が終わった。次の3体のサブエージェントを並列で起動し、
報告を P0 から P2 に整理して返すこと。
- design-reviewer: プランドキュメント（docs/plans/）との乖離
- edge-case-reviewer: 異常系と境界値の抜け
- security-reviewer: セキュリティ観点
```

## 7. 人間のレビュー（AIへの壁打ち）

```text
実装した[機能名]について、レビューする私に説明すること。判定はしなくてよい。
1. 変更の要点を、データの流れがわかる粒度で説明する。
2. 設計判断を3つまで挙げ、それぞれ採らなかった選択肢と併記する。
3. 各判断の根拠が docs/plans/[プランファイル].md のどこにあるかを引用して示す。
   プランに書いていないものは「実装時の判断」と明示する。
4. 壊れたときに影響が大きい箇所を、理由とともに挙げる。
根拠を確認できないものは推測で埋めず「不明」と答えること。
```

## 8. テストを保ったリファクタ

```text
[対象ディレクトリ]をリファクタリングすること。機能の変更はしない。
先に対象のテストを実行して全部 Green であることを確認し、
そこから1変更ごとにテストを回して、Green を保ったまま進めること。
観点: 1ファイル1責務に反する肥大したファイルの分割、
重複した処理の集約、.cursor/rules/architecture.mdc との乖離の解消。
テストが赤くなったら、その変更を巻き戻して報告すること。
```
